# 1단계 학습 과제

[1단계 설계](phase1-design.md)를 실제로 만들기 위한 과제 목록이다.

## 이 문서의 규칙

- **한 과제가 끝나면 다음 과제를 낸다.** 미리 다 쓰지 않는다.
- 다음 과제의 내용은 이번 과제에서 **무엇을 봤느냐**에 따라 달라져야 한다.
  재시도가 실제로 폭발하는 것을 본 뒤에 내는 과제와, 보기 전에 미리 쓴 과제는 다르다.
- 구현은 구현자가 한다. 이 문서는 목표와 성공 기준, 제약, 생각할 거리를 준다.
  정답 코드는 주지 않는다.

## 두 개의 축

과제는 STEP만으로 구성되지 않는다. 두 축이 교차한다.

| 축 | 내용 |
|---|---|
| **STEP** | 락 없음 → `synchronized` → 낙관적 → 비관적 → 분산락 → 대기열 |
| **기능 슬라이스** | 최소 도메인 → 선점 → 결제 → HTTP → 인증 → 드롭·수량 제한 |

최소 슬라이스로 STEP을 겪고, 기능을 붙이면서 다시 STEP을 밟는다.
한 과제에 두 축을 동시에 얹지 않는다. **한 번에 하나만 바꾼다** —
그래야 무엇 때문에 달라졌는지 알 수 있다.

## 진행 상황

| | 과제 | 축 | 상태 |
|---|---|---|---|
| 1 | 락 없는 재고 차감과 초과 판매 관찰 | STEP 0 · 최소 도메인 | 완료 |
| 2 | `synchronized`로 초과 판매 막기 | STEP 1 · 최소 도메인 | 완료 |
| 3 | 인스턴스를 나눠 `synchronized` 깨뜨리기 | STEP 1 · 최소 도메인 | 보류 |
| 4 | 낙관적 락으로 줄 세우지 않고 막기 | STEP 2 · 최소 도메인 | **진행 중** |

과제 3은 출제하지 않고 보류한다. 인스턴스를 2개 만드는 방식은 모니터가 갈라지는 것만
흉내 낼 뿐이고, 그 결론(`synchronized`는 객체 단위라 프로세스를 넘지 못한다)은 이미
과제 2에서 확인했다. **실제로 JVM을 나눠 보는 것은 HTTP 컨트롤러가 생긴 뒤** 부하
도구와 함께 다룬다. 그때가 되면 흉내가 아니라 진짜 측정이 된다.

# 과제 1 — 락 없는 재고 차감과 초과 판매 관찰

## 목표

**초과 판매를 직접 낸다.**

락을 걸지 않고 재고를 차감하는 최소 구현을 만들고, 동시 요청을 쏟아부어
재고보다 많이 팔리는 것을 눈으로 확인한다.

이 과제의 성공은 **테스트가 실패하는 것**이다. 통과하면 실패다.
락이 왜 필요한지 모른 채 락부터 걸면, 그 락이 정말 필요한지 영영 알 수 없다.

## 만들 것

최소 슬라이스다. 이보다 적게는 만들 수 없고, 이보다 많이 만들 필요는 없다.

- **SKU와 재고** — 파는 단위와 남은 수량
- **주문 생성** — 사용자 ID와 SKU, 수량을 받아 재고를 차감하고 주문을 남긴다
- **스키마** — Flyway 마이그레이션
- **동시성 테스트** — Testcontainers로 실제 MySQL을 띄우고 동시 요청을 재현

## 만들지 않을 것

지금 넣으면 관찰이 흐려지거나 시간만 먹는 것들이다.

| | 왜 미루는가 |
|---|---|
| 선점(Hold) | 경합은 재고 차감에서 일어난다. 선점은 결제가 들어올 때 필요해진다 |
| 결제 | 아직 부를 대상이 없다 |
| HTTP 컨트롤러 | 테스트가 서비스를 직접 부르면 된다. STEP 1에서 Gatling이 필요해질 때 만든다 |
| 인증 | 사용자 ID를 파라미터로 받으면 충분하다 |
| 드롭, 1인 수량 제한 | 기능 축이다. STEP을 먼저 겪는다 |
| Docker Compose | Testcontainers가 테스트용 DB를 띄운다. 앱을 띄울 때 필요해진다 |

## 성공 기준

1. **동시성 테스트가 초과 판매로 실패한다.** 재고 100개에 동시 요청 1,000건을 넣었을 때
   성공 건수가 100을 넘거나 최종 재고가 음수가 된다.
2. **그 실패가 재현된다.** 10번 돌려 대부분 재현되어야 한다. 어쩌다 한 번 나오는 것은
   관찰이 아니라 운이다.
3. **실제 MySQL에서 돈다.** H2에서 났다면 의미가 없다.
4. **측정 기록이 남는다** — `docs/experiments/00-no-lock.md`.

## 지켜야 할 제약

[1단계 설계](phase1-design.md)에서 정한 것들이다.

- 패키지는 도메인형으로 나눈다. 재고는 `inventory`, 주문은 `order`, SKU는 `catalog`.
- **역방향 참조를 만들지 않는다.** `inventory`가 `order`를 알면 안 된다.
- **도메인 간 참조는 엔티티가 아니라 ID로만.** `Order.userId`이지 `Order.user`가 아니다.
- 스키마는 Flyway로 만든다. `ddl-auto`로 만들지 않는다.
- 테스트를 먼저 쓴다. 구현이 먼저 나오면 순서가 틀린 것이다.

의존성은 버전 카탈로그를 거친다.
방법은 [의존성 추가 방법](getting-started.md#의존성-추가-방법)에 있다.
이번에 필요한 것 — Spring Data JPA, MySQL 드라이버, Flyway(코어 + MySQL),
Testcontainers(JUnit 5 + MySQL).

## 생각해볼 것

답을 주지는 않겠다. 막히면 물어보시면 된다.

**1. 재고 차감을 어떻게 쓸 것인가**

"읽고 → 검사하고 → 쓴다"로 구현하면 어느 지점에서 다른 스레드가 끼어들 수 있는가.
읽는 시점과 쓰는 시점 사이에 무엇이 일어날 수 있는지 그려보면 왜 깨지는지 보인다.

**2. 스레드를 진짜 동시에 출발시켜야 한다**

`for` 루프로 1,000개를 순차 실행하면 경합이 일어나지 않는다.
먼저 만든 스레드가 이미 일을 끝낸 뒤에 다음 스레드가 시작되기 때문이다.
모든 스레드를 **한 지점에 모아놓고 동시에 출발시키는** 장치가 필요하다.

**3. 재현이 안 되면 의심할 것**

초과 판매가 안 나거나 가끔만 난다면 실제로는 동시 실행이 안 되고 있을 가능성이 크다.

- DB 커넥션 풀 크기가 동시 요청 수보다 훨씬 작으면 실제 동시성은 풀 크기로 제한된다.
  HikariCP 기본값이 몇인지 확인해볼 것.
- 트랜잭션 경계가 어디에 있는가. 너무 좁으면 겹치는 구간이 짧아진다.
- 재고를 줄이거나(100 → 10) 동시 요청을 늘리면 경합 확률이 올라간다.

**4. 무엇을 기록할 것인가**

성공 건수만 보면 절반만 아는 것이다. 최종 재고, 실패한 요청과 그 원인,
소요 시간도 함께 봐야 다음 STEP에서 비교가 된다.

## 기록 형식

`docs/experiments/00-no-lock.md`로 남긴다. 디렉터리는 이때 만든다.

## 결과

## 막히면

- **개념이 안 잡힐 때** — 무엇이 헷갈리는지 말씀해 주시면 설명하겠다.
- **재현이 안 될 때** — 위 3번을 먼저 확인하고, 그래도 안 되면 조건을 알려달라.
- **코드를 봐줬으면 할 때** — 커밋하고 알려주시면 리뷰하겠다.

정답 코드를 먼저 주지는 않는다. 힌트와 설명이 먼저고, 그래도 막히면 그때 예시를 준다.

# 과제 2 — `synchronized`로 초과 판매 막기

## 목표

**초과 판매를 0으로 만들고, 그 대가를 측정한다.**

STEP 0에서 재고 100짜리를 1,000개 팔았다. 이번에는 정확히 100개만 팔리게 한다.
정확해진 대가로 무엇을 잃는지 숫자로 남긴다.

이번 과제의 성공은 **테스트가 통과하는 것**이다. STEP 0에서 주석 처리한 테스트를
되살려서 통과시킨다.

## 만들 것

- `OrderService.placeOrder`의 재고 차감 구간을 `synchronized`로 보호
- 주석 처리된 동시성 테스트 복구
- 측정 기록 `docs/experiments/01-synchronized.md`

## 성공 기준

1. **초과 판매 0.** 성공 100건, 최종 재고 0, 실패 900건(재고 부족)
2. **10회 재현.** 10회 모두 같은 숫자가 나와야 한다
3. **측정 기록이 남는다** — STEP 0과 나란히 비교할 수 있는 형태로

## 지켜야 할 제약

- STEP 0의 측정 조건을 바꾸지 않는다 — 재고 100, 요청 1,000, 커넥션 풀 50.
  조건이 달라지면 비교가 무의미해진다.
- `@Transactional`을 떼지 않는다. 원자성은 여전히 필요하다.
- 락 범위 외에 다른 것을 함께 바꾸지 않는다.

## 생각해볼 것

**1. 락과 트랜잭션 중 무엇이 바깥인가**

`@Transactional`은 AOP 프록시가 메서드 바깥에서 여닫고, `synchronized`는 메서드
안에 있다. 그대로 두면 락이 먼저 풀리고 커밋이 나중이다. 그 틈에 들어온 스레드는
무엇을 읽게 되는가. 초과 판매가 0이 안 나오면 여기를 먼저 의심한다.

**2. 무엇을 잠그고 있는가**

`synchronized`는 재고가 아니라 객체(모니터)를 잠근다. 메서드에 붙이면 SKU가 달라도
서로 기다린다. 지금 테스트는 SKU가 하나뿐이라 이 비용이 드러나지 않는다.
드러내려면 무엇을 바꿔야 하는가.

**3. 시간이 얼마나 나빠지는가**

줄을 세우면 동시 실행이 1이 된다. STEP 0의 2,249ms와 비교해 몇 배가 되는지 본다.
그 숫자가 STEP 2로 가야 할 이유가 된다.

## 기록 형식

`docs/experiments/01-synchronized.md`. STEP 0과 같은 틀에 비교 열을 둔다.

| 지표 | STEP 0 | STEP 1 |
|---|---|---|
| 성공 건수 | 1,000 | |
| 최종 재고 | 78 | |
| 초과 판매 | 900 | |
| 실패 건수 | 0 | |
| 소요 시간 | 2,249ms | |

## 막히면

과제 1과 같다. 힌트와 설명이 먼저고, 정답 코드는 최후 수단이다.

# 과제 4 — 낙관적 락으로 줄 세우지 않고 막기

## 목표

**줄을 세우지 않고 초과 판매를 막고, 그 대신 생기는 비용을 본다.**

STEP 1의 `synchronized`는 정확했지만 두 가지 대가를 치렀다. 모든 주문이 SKU와
무관하게 한 줄로 섰고(전부 성공하는 조건에서 59% 느려짐), 그 보호는 JVM 하나
안에서만 유효했다.

낙관적 락은 아무도 막지 않는다. 대신 **쓸 때 "내가 읽은 뒤로 누가 건드렸나"를
확인**해서, 건드렸으면 실패시킨다. 충돌이 없으면 거의 공짜고, 충돌이 잦으면
재시도가 쌓인다.

이번 과제의 성공은 **초과 판매가 0이면서, 낙관적 락이 언제 유리하고 언제 불리한지가
숫자로 갈리는 것**이다.

## 만들 것

- `Sku`에 버전 컬럼 — 엔티티와 Flyway 마이그레이션 양쪽
- 충돌 시 재시도
- `synchronized` 제거
- 측정 기록 `docs/experiments/02-optimistic-lock.md`

## 성공 기준

1. **초과 판매 0.** STEP 1과 같은 조건에서 성공 100건, 최종 재고 0
2. **10회 재현**
3. **두 조건을 나눠 측정한다.** 이게 이번 과제의 핵심이다
   - **몰림** — SKU 1개에 1,000건
   - **분산** — SKU 10개에 각 100건
4. **재시도 횟수를 센다.** 성공/실패만 보면 낙관적 락의 비용이 안 보인다
5. **측정 기록이 남는다** — STEP 1과 나란히 비교되는 형태로

## 지켜야 할 제약

- **`synchronized`를 제거한다.** 둘 다 남아 있으면 무엇이 일하는지 알 수 없다
- 스키마는 Flyway로 바꾼다. `ddl-auto`로 만들지 않는다
- 측정 조건을 바꾸지 않는다 — 재고 100, 요청 1,000, 커넥션 풀 50
- `@Transactional`은 유지한다

## 생각해볼 것

**1. 충돌은 언제, 어디서 감지되는가**

버전 검사는 UPDATE 문에 조건으로 붙는다. 그렇다면 충돌은 메서드 안에서 나는가,
커밋 시점에 나는가? 어떤 예외가 올라오는가? 그 예외를 **어디서 잡아야** 하는지가
다음 질문과 이어진다.

**2. 재시도를 어디에 두는가**

트랜잭션 **안**에서 재시도하면 안 된다. 이미 롤백 표시가 붙은 트랜잭션에서 다시
시도해봐야 소용없고, 무엇보다 읽은 값이 여전히 낡았다. 그러면 재시도는 어디에
있어야 하는가 — STEP 1에서 락을 놓았던 그 자리를 떠올려 보면 된다.

**3. 재시도에 한도가 필요한가**

1,000건이 한 SKU에 몰리면 재시도가 몇 번까지 갈 수 있는가. 한도가 없으면 무엇이
일어나는가. 한도에 걸린 요청은 사용자에게 무엇으로 보여야 하는가.

**4. 몰림과 분산에서 무엇이 달라질 것 같은가**

측정 전에 예상을 적어두고 결과와 비교한다. 빗나간 예측이 맞은 예측보다 많은 것을
알려준다.

## 기록 형식

`docs/experiments/02-optimistic-lock.md`.

| 지표 | STEP 1 (`synchronized`) | STEP 2 몰림 | STEP 2 분산 |
|---|---|---|---|
| 성공 건수 | 100 | | |
| 최종 재고 | 0 | | |
| 초과 판매 | 0 | | |
| 실패 건수 | 900 | | |
| 재시도 횟수 | 해당 없음 | | |
| 소요 시간 | 1,242ms | | |

## 막히면

과제 1과 같다.

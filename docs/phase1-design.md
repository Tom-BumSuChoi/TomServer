# 1단계 설계 — 한정 드롭 판매

- **상태**: 잠정 — 학습을 진행하며 바뀔 수 있다
- **날짜**: 2026-09-20
- **축**: 쓰기 경합 ([ADR-0001](adr/0001-three-difficulty-axes.md))

전체 맥락은 [로드맵](roadmap.md)에, 각 결정의 근거는 [ADR](adr/)에 있다.
이 문서는 **1단계를 어떤 구조로 만드는가**의 현재 방향을 정한다.

**확정된 명세가 아니다.** 만들어보면 틀린 것이 나오고, 그때 이 문서를 고친다.
바꿀 때는 바꾼 이유를 함께 남긴다. 계획이 바뀌는 것은 실패가 아니다.

이 문서는 스키마와 필드 목록을 정하지 않는다. 그것은 구현자가 설계한다.
여기서는 **무엇이 필요하고 무엇이 반드시 참이어야 하는가**만 정한다.
그중에서도 **불변식(2장)이 가장 오래 살아남을 부분**이다 — 구조는 바뀌어도
"초과 판매는 0이다"는 바뀌지 않는다.

---

## 1. 범위

**포함** — 로스터리, 원두 상품, SKU(중량·분쇄도), 로스터리 권장 레시피, 재고,
한정 드롭(오픈 시각), 다중 상품 주문, **1인 구매 수량 제한**, 재고 선점,
결제(가짜 어댑터), OAuth 로그인.

1인 구매 수량 제한을 넣는 이유는 **재고 경합과 다른 축의 동시성 문제**이기 때문이다.
재고는 SKU 단위로 경합하지만 수량 제한은 사용자 단위로 경합한다. 같은 사용자가
동시에 여러 요청을 보내면 제한을 뚫을 수 있다. 공짜로 얻는 연습거리다.

**제외** — 배송·물류, 리뷰, 검색, 쿠폰, 장바구니, 관리자 기능(데이터는 시드),
실제 PG, 정산(2단계), 공동구매(2단계), 레시피 공유·피드(3단계).

장바구니를 넣지 않는 이유는 경합과 무관한 CRUD여서 배울 것이 없기 때문이다.
권장 레시피를 넣는 이유는 `catalog`에 딸린 데이터일 뿐이라 비용이 0에 가깝고
제품이 그럴싸해지기 때문이다.

## 2. 도메인 모델

### 개념과 책임

| 개념 | 책임 | 비고 |
|---|---|---|
| 사용자 | 구매자 | `auth`가 소유한다. 다른 도메인은 ID로만 참조 |
| 로스터리 | 판매자 | 2단계 정산 대상, 3단계 팔로우 대상 |
| 원두 상품 | 무엇을 파는가 | 권장 레시피가 여기 붙는다 |
| SKU | 판매 단위 (원두 × 중량 × 분쇄도) | 가격의 단위 |
| 재고 | 몇 개 남았는가 | **경합의 전부가 여기에 있다** |
| 드롭 | 오픈 시각이 있는 한정 판매 | 핫스팟을 만드는 장치 |
| 선점 | 누가, 어느 재고를, 언제까지 | 만료가 핵심 |
| 주문 | 결제 대기부터 확정까지의 구매 상태 | 확정 후 2단계 정산의 입력 |
| 결제 | 인터페이스 + 가짜 구현체 | 실패·지연 주입 가능 |

### 재고 선점 흐름

주문을 만들면 결제가 끝날 때까지 재고를 잡아둔다.
결제 중에 다른 사람이 재고를 채가면 안 되기 때문이다.

```
재고 가용
  ──주문 생성(선점)──> 주문에 묶임
                        ├─ 결제 성공 ──> 차감 확정
                        ├─ 확정 실패 ──> 선점 유지, 다른 수단으로 재시도
                        ├─ 결과 불명 ──> 선점 유지, 결과 확인 전 새 결제 보류
                        └─ 시간 만료·미결제 확인 ──> 주문 취소, 재고 복구
```

확정 실패만으로 주문을 취소하지 않는다. 선점 기한 안에는 같은 주문으로 결제를
재시도할 수 있어야 다른 결제 수단을 선택할 수 있다. 타임아웃은 결제 실패가 아니라
결과 불명일 수 있으므로, 결제사 조회나 후속 알림으로 결과를 확인하기 전에는
재고를 복구하거나 새 결제를 시도하지 않는다. 선점이 만료되어도 결과가 불명확하면
먼저 결제 여부를 확인하고, 미결제가 확인된 경우에만 복구한다.

### 불변식

**이 목록이 1단계의 실질적인 명세다.** 각 항목은 그대로 테스트가 된다.

1. **초과 판매는 0이다.** 확정 차감 + 유효 선점의 합은 총 재고를 넘지 않는다.
2. **미판매도 0이어야 한다.** 재고가 남았는데 살 수 없는 상태가 되면 락이 과한 것이다.
3. **선점은 영원히 남지 않는다.** 확정되거나, 취소되거나, 만료된다.
4. **같은 멱등키의 요청은 주문을 하나만 만든다.** 재시도해도 결과가 같다.
5. **1인 구매 수량 제한은 동시 요청으로 뚫리지 않는다.**
6. **확정 실패나 결과 불명만으로 선점을 해제하지 않는다.** 결제 성공 시 확정하고,
   미결제 상태로 선점이 만료된 경우에만 재고를 복구한다.
7. **주문 확정과 재고 차감은 함께 성립하거나 함께 실패한다.**

2번을 빠뜨리기 쉽다. 락을 너무 크게 걸어 재고가 남았는데 팔리지 않는 상태도
**실패로 판정한다.** 정확성만 보면 락을 과하게 거는 쪽으로 도망갈 수 있다.

## 3. 패키지 구조와 의존 방향

1단계는 단일 모듈이다 ([ADR-0004](adr/0004-single-module-phase1.md)).

```
kr.kro.tomchi.tomserver
├── auth/         OAuth, 토큰 발급·검증
├── roastery/     로스터리
├── catalog/      원두 상품, SKU, 권장 레시피
├── inventory/    재고, 선점, 드롭
├── order/        주문
└── payment/      결제 인터페이스 + 가짜 구현체
```

```
order ──> inventory ──> catalog ──> roastery
  └────> payment
auth 는 어느 것에도 의존하지 않는다
```

**규칙 둘.**

- 역방향 참조를 만들지 않는다. `inventory`가 `order`를 알면 안 된다.
- **도메인 간 참조는 엔티티가 아니라 ID로만 한다.** 조인이 필요하면 조회 계층에서 합친다.

이 선이 곧 2단계의 모듈 경계선이다. 지금 불편해도 지켜야 나중에 뜯지 않는다.

## 4. 인증

서버 주도 OAuth, 자체 토큰 발급 ([ADR-0006](adr/0006-oauth-server-led.md)).

```
앱 ──시스템 브라우저──> 서버 /oauth2/authorization/google
서버 <──인가 코드 교환──> 구글
앱 <──커스텀 스킴── 서버가 발급한 자체 토큰
```

| | 액세스 토큰 | 리프레시 토큰 |
|---|---|---|
| 형태 | 자체 JWT | 불투명 문자열 |
| 만료 | 짧게 (30분 내외) | 길게 (2주 내외) |
| 저장 | 안 함 (stateless) | Redis |

리프레시 토큰은 회전하고, 한 번 쓴 토큰이 다시 들어오면 탈취로 간주해
해당 사용자의 전체 세션을 무효화한다.

### 불변식

1. 만료된 액세스 토큰으로는 어떤 보호 자원에도 접근할 수 없다.
2. 회전된 리프레시 토큰은 두 번 쓸 수 없다.
3. 재사용이 탐지되면 그 사용자의 모든 리프레시 토큰이 무효화된다.
4. 앱 인스턴스가 2개여도 위 셋이 모두 성립한다.

4번이 인증을 난이도 축과 연결시킨다. 액세스 토큰은 stateless라 문제가 없지만,
리프레시 토큰의 상태는 인스턴스 간에 공유되어야 한다.

## 5. 동시성 전략

**락 없이 시작한다.** STEP을 오르며 각 방법이 어디서 무너지는지 측정한다
([ADR-0008](adr/0008-no-lock-abstraction.md)).

| | 방법 | 통하는 상황 | 무너지는 지점 |
|---|---|---|---|
| 0 | 락 없음 | — | 초과 판매 발생 |
| 1 | `synchronized` | 단일 인스턴스 | 인스턴스 2개에서 즉시 깨짐 |
| 2 | 낙관적 락 | SKU 경합이 흩어진 상태 | 단일 SKU 핫스팟에서 재시도 폭발 |
| 3 | 비관적 락 | 핫스팟에서도 정확 | 커넥션 점유 → 처리량 한계 |
| 4 | Redis 분산락 | DB 부하를 덜어냄 | 락 타임아웃·TTL 만료라는 새 문제 |
| 5 | 대기열 | 경합 자체를 직렬화 | 복잡도, 사용자 대기 UX |

락 전략은 인터페이스로 추상화하지 않는다. 재고 차감 로직을 한 곳에 모아 직접 교체한다.

### STEP마다 기록할 것

| 지표 | 왜 보는가 |
|---|---|
| 초과 판매 건수 | 0이 아니면 그 STEP은 실패 |
| 미판매 잔여 재고 | 락이 과한지 |
| 성공률과 실패 원인 분포 | 재시도 소진인지 락 타임아웃인지 |
| 처리량(TPS)과 p99 | STEP이 올라가며 나아지는지 |
| DB 커넥션 대기 시간 | 병목이 어디로 옮겨갔는지 |
| CPU 사용률 | 포화 구간의 수치는 비교에 쓰지 않는다 |

### 데드락

주문 하나가 재고 레코드 여러 개를 잠근다. 순서를 고정하지 않으면 교착한다.

```
주문 A: SKU-7 잠금 → SKU-3 대기
주문 B: SKU-3 잠금 → SKU-7 대기     ← 교착
```

**SKU ID 오름차순으로 정렬한 뒤 잠근다.**
먼저 데드락을 재현하는 테스트를 만들고, 실제로 터지는 것을 확인한 다음 정렬을 넣는다.

### 선점 만료

**lazy 정리가 주 방식이다.** 누군가 그 SKU를 사려는 시점에 만료되고 미결제가
확인된 선점을 함께 정리한다. 결과 불명인 결제는 확인 전까지 정리하지 않는다.
경합이 있는 곳에서 자동으로 정리되므로 비용이 거의 없다.

**주기 배치를 백업으로 둔다.** 아무도 사지 않는 SKU의 선점은 lazy로 정리되지 않아
재고 표시가 틀리게 된다. 배치도 미결제 확인 전에는 선점을 복구하지 않는다.
이 배치는 인스턴스 2개에서 중복 실행되므로
**여기서도 분산락이 필요하다** — STEP 4의 결과물을 재사용한다.

### 멱등성

클라이언트가 요청마다 고유 키를 보내고, 서버는 그 키로 결과를 기억한다.
같은 키가 다시 오면 새로 처리하지 않고 이전 결과를 그대로 돌려준다.

2단계 정산의 토대가 된다. 1단계에서 습관을 들이지 않으면 2단계에서 전부 다시 만든다.

## 6. 데이터와 인프라

| 항목 | 선택 | 근거 |
|---|---|---|
| DB | MySQL | [ADR-0005](adr/0005-mysql.md) |
| 캐시·락 | Redis | 리프레시 토큰, 분산락, 배치 중복 방지 |
| 스키마 | Flyway | `ddl-auto`로 운영 스키마를 건드리지 않는다 |
| 로컬·서버 구성 | Docker Compose | 인스턴스 2개는 STEP 1에서 |
| 인스턴스 분산 | nginx 컨테이너 | OCI LB(10 Mbps)는 측정 병목이라 쓰지 않는다 |

### OCI 메모리 예산 (4 OCPU / 24 GB)

| 구성요소 | 메모리 |
|---|---|
| MySQL | 4 GB |
| Redis | 1 GB |
| 앱 인스턴스 × 2 | 4 GB |
| nginx | 100 MB |
| 모니터링 (STEP 3~4에서) | 2 GB |
| OS·여유 | 2 GB |
| **합계** | **~13 GB / 24 GB** |

여유가 있다. 다만 **부하를 걸 때 4 OCPU를 앱·DB·Redis가 나눠 쓰므로**
CPU 사용률을 함께 기록하고 포화 구간은 STEP 비교에서 제외한다.

모니터링(Prometheus + Grafana)은 지금 올리지 않는다.
STEP 0~2는 Gatling 리포트와 Actuator 메트릭으로 충분하다.
병목 위치를 알고 싶어지는 STEP 3~4에서 붙인다.

## 7. 테스트와 검증

| 계층 | 무엇을 검증 | 도구 | STEP |
|---|---|---|---|
| 단위 | 도메인 규칙 | JUnit | 전부 |
| 통합 | 실제 DB에서 불변식 1~7 | Testcontainers + 스레드 | 0~3 |
| 부하 | 인스턴스 2개, 처리량, p99 | Gatling | 1~5 |

STEP 0~3의 주 검증 수단은 통합 테스트다.

```
N개 스레드가 CountDownLatch 하나를 기다리다 동시에 출발
  → 실제 MySQL에 같은 SKU 주문
  → 불변식 검증
```

**STEP 1의 핵심은 통합 테스트로 재현할 수 없다.** 테스트가 JVM 하나 안에서 돌아
`synchronized`가 정상 동작해 버린다. 여기서부터 Docker Compose로 앱을 2개 띄우고
Gatling으로 외부에서 부하를 건다. STEP 1이 부하 테스트 환경을 처음 구축하는 시점이다.

순서는 항상 **실패하는 테스트 먼저**다 ([개발 규약](conventions.md#테스트)).
락 없는 구현에서 완료 기준 테스트가 실패하는 것을 확인하고 시작한다.

## 8. 완료 기준

> 한정 드롭 재고 100개에 동시 요청 1,000건이 몰릴 때
> **성공이 정확히 100건, 최종 재고 0, 초과 판매 0건.**
> 앱 인스턴스를 2개로 늘려도 같은 결과가 나온다.
> 서로 다른 SKU 조합의 주문이 교차해도 데드락으로 실패하는 요청이 없다.

여기에 불변식 1~7과 인증 불변식 1~4가 모두 통과해야 한다.

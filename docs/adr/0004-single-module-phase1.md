# ADR-0004: 1단계 단일 모듈 시작

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: [ADR-0003](0003-phased-by-axis.md)

## 배경

프로젝트를 멀티모듈로 키울 계획이고, 그래서 Gradle 버전 카탈로그를 먼저 도입했다.
남은 질문은 **언제 나눌 것인가**였다.

## 결정

1단계는 **단일 모듈**로 시작한다. 도메인형 패키지로 경계선만 미리 긋고,
2단계에서 정산이 들어올 때 모듈로 분리한다.

```
kr.kro.tomchi.tomserver
├── auth/         OAuth, 토큰 발급·검증
├── roastery/     로스터리
├── catalog/      원두 상품, SKU        ← 거의 안 변하고 많이 읽힘
├── inventory/    재고, 선점            ← 경합의 전부
├── order/        주문
└── payment/      결제 인터페이스 + 가짜 구현체
```

의존 방향: `order → inventory → catalog → roastery`, `order → payment`.
`auth`는 어느 것에도 의존하지 않는다. **역방향 참조는 없다.**

## 근거

- 멀티모듈의 진짜 이득은 "정산 코드가 주문 테이블을 직접 읽고 싶어질 때 컴파일러가
  막아주는 것"인데, **그 유혹이 1단계에는 없다.** 도메인이 여섯 덩어리뿐이다.
- 먼저 나누면 빌드 설정만 복잡해지고 얻는 것이 없다.
- 패키지 경계를 나중의 모듈 경계선에 맞춰 그어두면 전환 비용이 낮다.

`catalog`와 `inventory`를 일부러 나눈 것은 성격이 정반대이기 때문이다.
카탈로그는 거의 변하지 않고 많이 읽히며 3단계에서 읽기 확장의 대상이 된다.
재고는 초당 수백 번 경합한다. 캐시 전략도 락 전략도 따로 가야 한다.

## 기각한 대안

**선제적 멀티모듈 분할** — 처음부터 `:api` `:domain` `:infra` 등으로 나누는 방식.
기각 이유: 지금 얻는 것이 없고 빌드 복잡도만 늘어난다.

**ArchUnit으로 경계 강제** — 단일 모듈에서 의존 방향을 테스트로 막는 방식.
기각 이유: 패키지 6개는 손으로 지킬 수 있고, 규칙을 어길 사람이 한 명뿐이다.
도입 비용은 낮지만 지금 필요한 문제를 풀지 않는다.

## 결과

- 의존 방향을 **수동으로** 지켜야 한다. `import` 한 줄이면 깨진다.
- **도메인 간 참조는 엔티티가 아니라 ID로만 한다.**

  ```
  ❌  Order.user: User          — auth 를 끌고 들어옴
  ✅  Order.userId: UserId      — 값만 가짐
  ```

  조인이 필요하면 조회 계층에서 합친다. 이 규칙을 안 지키면 모듈 분리 시 전부 뜯게 된다.
- 2단계 진입 시 예상되는 분리 형태는 `:core` `:commerce` `:settlement` `:api`이나,
  확정된 것은 아니다.

# 01 — `synchronized`

- 날짜: 2026-09-24
- STEP: 1 (`synchronized`)
- 환경: 로컬 / MySQL 8.0 (Testcontainers) / JDK 25

## 무엇을 했나

STEP 0에서 초과 판매가 나던 재고 차감을 `synchronized`로 막았다.

락을 어디에 두느냐가 이번 STEP의 전부였다. 처음에는 `OrderService.placeOrder`에
`@Synchronized`를 붙였는데 초과 판매가 그대로 900건 났다. `@Transactional`은
AOP 프록시가 메서드 호출을 **바깥에서** 감싸고 `@Synchronized`는 메서드 **안**에
있어서, 락이 먼저 풀리고 커밋이 나중이었기 때문이다.

```
스레드 A: [BEGIN] → [모니터 획득] 읽기(100) 차감 저장 [모니터 해제] → [COMMIT]
스레드 B:    [BEGIN] ────── 대기 ──────→ [모니터 획득] 읽기(100)
                                                    ↑ A는 아직 커밋 전
```

락은 줄을 세웠지만 줄 선 스레드들이 전부 아직 커밋되지 않은 같은 값을 읽었다.
**임계 구간이 트랜잭션보다 짧았다.**

그래서 락을 트랜잭션보다 바깥으로 빼야 했다. 트랜잭션 경계는 프록시가 메서드
호출을 감싸서 만들므로, 락은 그 메서드를 **호출하는 쪽**에 있어야 한다. 같은
클래스 안에서 메서드를 쪼개면 자기 호출이라 프록시를 거치지 않아 `@Transactional`이
아예 무시되므로, **별도 빈**이 필요했다.

```
PlaceOrderUseCase   @Component   @Synchronized execute()      ← 락 (바깥)
OrderService        @Service     @Transactional placeOrder()  ← 트랜잭션 (안)
```

## 조건

STEP 0과 동일하다. 비교를 위해 바꾸지 않았다.

| | |
|---|---|
| 초기 재고 | 100 |
| 동시 요청 | 1,000 |
| 요청당 수량 | 1 |
| 커넥션 풀 | 50 (HikariCP) |
| 트랜잭션 | `@Transactional` 있음 |

## 결과

10회 반복. **10회 모두 동일한 값이 나왔다.**

| 지표 | STEP 0 | STEP 1 |
|---|---|---|
| 성공 건수 | 1,000 | **100** |
| 최종 재고 | 78 | **0** |
| 초과 판매 | 900 | **0** |
| 실패 건수 | 0 | **900** (재고 부족) |
| 소요 시간 | 평균 2,249ms | 평균 1,242ms |

재고 편차도 사라졌다. STEP 0에서 77~79로 흔들리던 최종 재고가 10회 모두 정확히
0이다. 락이 걸린 뒤로는 실행 순서가 결과를 바꾸지 못한다.

### 소요 시간이 줄어든 것은 락이 싸서가 아니다

STEP 0의 2,249ms보다 오히려 1,000ms 빨라졌다. 락을 걸면 느려질 것이라는 예상이
빗나갔다.

이유는 **900건이 일을 하지 않았기 때문**이다. 재고 0을 읽고 즉시 예외로 빠져
UPDATE도 INSERT도 하지 않았다. 끝까지 일한 것은 100건뿐이다.
"정확해져서 할 일이 줄었다"이지 "락이 싸다"가 아니다.

## 락의 비용

락의 순수 비용을 보려면 모든 요청이 성공해야 한다. 재고를 1,000으로 올려
1,000건이 전부 끝까지 일하도록 만들고 락 유무만 바꿔 각 5회 측정했다.

| 재고 1,000 · 요청 1,000 | 락 없음 | 락 있음 |
|---|---|---|
| 성공 건수 | 1,000 | 1,000 |
| 최종 재고 | **977 ~ 978** | **0** |
| 소요 시간 | 평균 1,774ms | 평균 2,819ms |

**정확성의 값은 59% 느려지는 것이다** (2,819 / 1,774 ≈ 1.59배).

락 없는 쪽의 최종 재고 977이 더 중요하다. 1,000번 차감했는데 반영된 것은 23번뿐이다.
재고가 넉넉하면 이 버그는 **품절도 예외도 없이 조용히** 장부만 망가뜨린다.
STEP 0에서는 재고가 바닥나 증상이라도 보였지만, 여기서는 아무 신호가 없다.

## 무엇이 무너졌나

무너진 것은 없다. 이번 STEP의 목표는 달성됐다.

다만 **드러나지 않은 비용**이 있다. `synchronized`는 재고가 아니라 객체(모니터)를
잠근다. `PlaceOrderUseCase` 빈 하나를 잠그므로 **SKU가 달라도 서로 기다린다.**
지금 테스트는 SKU가 하나뿐이라 이 손해가 측정에 잡히지 않는다.

그리고 이 락은 **JVM 하나 안에서만** 유효하다. 인스턴스를 2개 띄우면 각 JVM이
자기 모니터만 잠그므로 STEP 0 상태로 돌아간다. 아직 확인하지 않았다.

## 다음에 할 것

**STEP 1 후속 — 인스턴스를 나눠 다시 깨뜨린다.**
`synchronized`가 프로세스 경계를 넘지 못한다는 것을 숫자로 확인한다.

그 다음 **STEP 2 — 낙관적 락.** 이번 STEP의 두 가지 손해를 겨냥한다.

- SKU가 흩어지면 충돌이 없으므로 거의 공짜가 된다 (지금은 무조건 직렬화)
- 락 대신 버전 충돌을 감지하므로 프로세스 경계를 넘는다

대신 한 SKU에 몰리면 재시도가 폭발하는 것을 보게 될 것이다.
기준선은 이번 STEP의 **2,819ms (재고 1,000 · 요청 1,000 · 전부 성공)** 이다.

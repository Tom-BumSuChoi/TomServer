# ADR-0001: 난이도 세 축을 학습 목표로 채택

- **상태**: 채택
- **날짜**: 2026-09-20

## 배경

연습용으로 큰 프로젝트를 만들기로 했으나 기획이 정해지지 않은 상태였다.
"대형 프로젝트"가 무엇을 뜻하는지부터 정의해야 했다.

## 결정

프로젝트의 규모를 **기능 개수가 아니라 난이도 세 축**으로 정의한다.

| 축 | 핵심 난제 |
|---|---|
| 쓰기 경합 | 같은 자원에 여러 요청이 동시에 |
| 정합성 | 여러 단계를 거치는 돈과 조건부 거래 |
| 읽기 확장 | 소수가 쓰고 다수가 읽음 |

## 근거

- 컨트롤러-서비스-리포지토리를 40번 반복해 쓰는 것은 1번 쓰는 것과 같은 것을 배운다.
  기능을 늘려도 학습량은 늘지 않는다.
- 중·고급이 갈리는 지점은 **제약의 빡셈**이다. 동시에 들이받을 때 답이 하나로 수렴하는지,
  외부 시스템이 죽었을 때 돈이 증발하지 않는지, 데이터가 많아져도 쿼리가 도는지.
- 이 제약들은 전부 **측정 가능하다.** "잘 동작한다"가 아니라 숫자로 판정할 수 있어서
  완료 기준으로 쓸 수 있다.

## 기각한 대안

**기능 개수로 규모 키우기** — 이커머스 전체를 잡고 회원가입·상품·장바구니·주문·리뷰를
차례로 만드는 방식.

기각 이유: 3개월 뒤에 CRUD 40개와 아키텍처 경험 0이 남는다. 연습용 대형 프로젝트가
실패하는 가장 흔한 경로다.

## 결과

- 기능 추가 판단 기준이 **"이걸 만들면 새로운 난제를 만나는가"** 로 고정된다.
  아니면 만들지 않는다.
- 모든 단계의 완료 기준을 숫자로 쓰게 된다.
- 화면에 보여줄 것이 적어질 수 있다. 포트폴리오 관점에서는 약점이 될 수 있으나,
  이 프로젝트의 목적은 실력 향상이므로 감수한다.

# ADR-0007: 푸시 채널로 FCM 채택

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: [ADR-0006](0006-oauth-server-led.md)

## 배경

3단계에서 신규 드롭·공동구매 오픈을 팔로워에게 알려야 한다.
클라이언트는 Android와 iOS 앱 둘 다이다.

## 결정

**FCM 단일 채널**을 쓴다. 구현은 3단계에서 한다.

## 근거

- **Android의 백그라운드 푸시는 FCM이 유일한 실용 경로다.** 자체 소켓을 유지하는 방법은
  배터리 최적화와 백그라운드 제약 때문에 실서비스에서 동작하지 않는다.
- iOS도 FCM이 APNs를 감싸주므로 채널을 하나로 유지할 수 있다.

## 기각한 대안

**Web Push (VAPID)** — 웹 브라우저라면 Firebase 없이 서버가 직접 발송할 수 있다.

기각 이유: 클라이언트가 앱이라 해당하지 않는다. (참고로 iOS Safari의 웹 푸시는
홈 화면에 추가한 경우에만 동작한다는 제약도 있다.)

**APNs 직접 연동** — iOS만이었다면 인증키(`.p8`)와 HTTP/2 연결로 Firebase를 완전히
뺄 수 있었다.

기각 이유: Android 때문에 어차피 FCM이 필요하다. 채널을 둘로 나누면 디바이스 토큰 관리와
발송 실패 처리를 두 벌 만들게 되어 관리 비용만 늘어난다.

## 결과

- Firebase가 프로젝트에 들어온다. 단 **인증에는 쓰지 않는다**
  ([ADR-0006](0006-oauth-server-led.md)). 용도는 푸시 하나로 제한한다.
- 디바이스 토큰 등록·갱신·폐기 관리, 발송 실패 재시도, 무효 토큰 정리가
  3단계 범위에 포함된다.
- 외부 서비스 의존이 하나 생긴다. "인프라를 OCI에 모은다"는 구성이 완전하지 않게 된다.
  푸시는 대안이 없으므로 감수한다.
- 이 결정은 3단계 진입 전까지 구현하지 않는다. 그 사이 클라이언트 계획이 바뀌면
  재검토한다. 알림 발송을 인터페이스로 끊어두면 구현체 교체로 대응할 수 있다.

# 개발 규약

## 패키지 구조

도메인형으로 묶는다. 최상위 분류는 계층이 아니라 **도메인**이다.

```
kr.kro.tomchi.tomserver
├── TomServerApplication.kt
└── <도메인>/              예: user, post
    ├── controller/
    ├── service/
    ├── repository/
    └── domain/
```

- 새 기능은 새 도메인 패키지에서 시작한다. 기존 도메인의 `service/`에 끼워 넣지 않는다.
- 여러 도메인이 공유하는 코드를 모으는 패키지(`common/` 등)는 **실제로 중복이 생긴 뒤에** 만든다.
  미리 만들어 두지 않는다.

## 브랜치

```
feature/*  ──rebase──▶  dev  ──squash──▶  main
```

- `main` — 배포 브랜치. `dev`에서 스쿼시한 버전 단위 커밋만 올라간다.
- `dev` — 통합 브랜치이자 저장소 기본 브랜치. PR의 기본 대상이다.
- `feature/<이름>` — 작업 단위. `dev`에 리베이스로 병합해 선형 히스토리를 유지한다.

초기 스캐폴딩(빌드 설정, 문서, 도메인 골격)까지는 `main`에 직접 커밋했다(`fcf2589`까지).
그 이후의 모든 변경은 `feature/` 브랜치를 거친다.

## 릴리스

- 버전은 [SemVer](https://semver.org/lang/ko/)를 따르고 Git 태그로 표기한다 (`v0.1.0`).
- 로드맵의 단계 완료를 MINOR로 잡는다. 1단계 완료가 `v0.1.0`이다.
- `dev → main` 스쿼시 커밋 제목은 `chore(release): v0.1.0` 형식으로 쓴다.

## 커밋 메시지

[Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/) 형식으로, 한국어로 쓴다.

```
<type>(<scope>): <subject>

- <본문 한 줄>
- <본문 한 줄>
```

- 제목과 본문 모두 **명사형**으로 끝낸다. 서술형·과거형·평서문·마침표를 쓰지 않는다.
- 본문은 `- ` 불렛으로 쓰고, 한 줄에 한 가지만 담는다.
- 본문에는 무엇을 했는지보다 **왜** 그렇게 했는지를 쓴다.

type은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `build`를 쓴다.
scope는 도메인 이름이나 변경 영역이며 생략할 수 있다.

| | 예시 |
|---|---|
| ✅ | `docs: 개발 환경 및 규약 문서 추가` |
| ✅ | `- 스켈레톤 단계에서 합의한 구조를 저장소에 고정` |
| ❌ | `docs: 문서를 추가했습니다` |
| ❌ | `- 문서가 없어서 추가했다` |

## 테스트

TDD로 간다. 실패하는 테스트를 먼저 쓰고, 통과시키는 최소 구현을 한다.

1. 실패하는 테스트 작성 → 실제로 실패하는지 확인
2. 통과시키는 최소 구현 → `./gradlew test` 통과 확인
3. 리팩터링 → 테스트가 계속 통과하는지 확인

- 테스트는 `src/test/kotlin`에 프로덕션 코드와 **같은 패키지 경로**로 둔다.
- 테스트 본문은 Given–When–Then 흐름으로 작성하고, 각 구간을 `// given`, `// when`, `// then` 주석으로 구분한다.
- 버그를 고칠 때도 버그를 재현하는 테스트를 먼저 쓴다.

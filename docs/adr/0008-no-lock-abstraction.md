# ADR-0008: 락 전략 비추상화와 STEP식 교체

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: [ADR-0001](0001-three-difficulty-axes.md), [ADR-0005](0005-mysql.md)

## 배경

1단계는 재고 경합을 여섯 STEP으로 오르며 배운다.

| | 방법 | 무너지는 지점 |
|---|---|---|
| 0 | 락 없음 | 초과 판매 발생 |
| 1 | `synchronized` | 인스턴스 2개에서 깨짐 |
| 2 | 낙관적 락 | 단일 SKU 핫스팟에서 재시도 폭발 |
| 3 | 비관적 락 | 커넥션 점유 → 처리량 한계 |
| 4 | Redis 분산락 | 락 타임아웃·TTL 만료라는 새 문제 |
| 5 | 대기열 | 복잡도, 사용자 대기 UX |

여섯 가지를 오가야 하니 전략 패턴으로 추상화할지가 문제였다.

## 결정

**추상화하지 않는다.** 재고 차감 로직을 한 곳에 모아두고, STEP을 오를 때마다
그 자리의 구현을 직접 갈아엎는다.

**STEP 0(락 없음)에서 시작한다.** 락을 미리 걸고 시작하지 않는다.

## 근거

- 한 번에 하나만 쓰고, STEP을 오르면 이전 구현은 버린다. 추상화하면 쓰지도 않을
  구현체 여섯 개를 떠안게 된다.
- **STEP마다 인터페이스가 맞지 않는다.** 낙관적 락은 재시도 루프가 필요하고,
  분산락은 획득 실패와 타임아웃을 다뤄야 하며, 대기열은 응답 자체가 비동기가 된다.
  같은 시그니처로 묶으면 억지 추상화가 된다.
- STEP의 목적은 "설정으로 전환 가능한 옵션 만들기"가 아니라 **각 방법이 무너지는 지점을
  직접 겪는 것**이다. 옵션으로 남겨두면 겪지 않고 넘어가게 된다.
- 락을 처음부터 걸어두면 **그 락이 정말 필요한지 영영 알 수 없다.**
  초과 판매가 실제로 나는 것을 봐야 한다.

## 기각한 대안

**`LockStrategy` 인터페이스 + 구현체 6개** — 설정으로 전환할 수 있어 STEP 비교가
편해 보인다.

기각 이유: 위에 적은 대로 STEP마다 필요한 제어 흐름이 달라 공통 시그니처가 성립하지 않는다.
쓰지 않을 코드를 유지하게 되며, 이는 프로젝트 지침이 금지하는 추측성 코드다.

## 결과

- STEP을 오를 때 코드를 **실제로 갈아엎는다.** STEP마다 커밋을 따로 남겨
  나중에 비교할 수 있게 한다.
- 측정 기록을 `docs/experiments/`에 남긴다. 무엇을 바꿨는지, 어떤 조건으로 측정했는지,
  숫자가 어떻게 나왔는지, 무엇이 무너졌는지.
  **코드는 STEP을 오르며 버려지지만 측정 기록은 남는다. 그것이 결과물이다.**
- 결제는 예외다. 가짜와 진짜가 **공존해야 하고** 테스트에서 실패·지연을 주입해야 하므로
  인터페이스를 둔다. 추측이 아니라 지금 당장 두 구현체가 필요한 경우다.

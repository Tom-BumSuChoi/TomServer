# ADR-0009: 실제 DB 기반 테스트

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: [ADR-0005](0005-mysql.md), [ADR-0008](0008-no-lock-abstraction.md)

## 배경

1단계 전체가 락 전략 비교다. 테스트를 어떤 DB로 돌릴지가 학습 성립 여부를 좌우한다.

## 결정

**Testcontainers**로 테스트마다 실제 MySQL과 Redis 컨테이너를 띄운다.

동시성 검증은 JVM 안에서 재현한다.

```
N개 스레드가 CountDownLatch 하나를 기다리다 동시에 출발
  → 실제 MySQL에 같은 SKU 주문
  → 성공 건수, 최종 재고, 초과 판매 검증
```

## 근거

- H2에서는 `SELECT FOR UPDATE`의 실제 동작도, 갭락도, 격리 수준 차이도 재현되지 않는다.
  **락이 진짜로 동작하지 않는 DB에서 락 전략을 비교하면 의미가 없다.**
- STEP 0~3은 이 방식으로 충분히 검증된다. 외부 부하 도구까지 꺼낼 필요가 없어
  빠르게 반복할 수 있다.
- 실제 컨테이너를 쓰면 CI에서도 같은 결과가 나온다.

## 기각한 대안

**H2 인메모리** — 빠르고 설정이 간단하다.

기각 이유: 이 프로젝트가 배우려는 것이 전부 사라진다. 속도를 얻고 목적을 잃는 거래다.

**로컬에 상시 띄워둔 공용 DB** — Testcontainers보다 빠르다.

기각 이유: 테스트 간 상태 격리가 깨진다. 동시성 테스트는 재고를 실제로 소진시키므로
격리가 없으면 결과를 신뢰할 수 없다. CI에서 재현도 어렵다.

## 결과

- **테스트가 느려진다.** 감수한다. 느린 것이 맞다.
- Docker가 개발 환경과 CI 양쪽에 필요하다.
- STEP 1의 핵심인 "인스턴스 2개에서 `synchronized`가 깨진다"는
  **이 방식으로 재현할 수 없다.** 테스트는 JVM 하나 안에서 돌기 때문에 오히려 정상
  동작한다. 여기서부터는 Docker Compose로 앱을 2개 띄우고 외부 부하 도구를 써야 한다
  ([ADR-0010](0010-gatling.md)).

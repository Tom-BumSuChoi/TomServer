# 로드맵

## 이 프로젝트는 무엇인가

스페셜티 커피 플랫폼. 생두에서 한 잔까지의 가치사슬을 다룬다.

```
생두 유통 ──> 로스팅 ──> 볶은 원두 ──> 추출 ──> 커피
(개별·공동구매)                    (레시피)   (드립백·음료)
```

실서비스 운영이 목적이 아니라 **백엔드 난제를 직접 겪는 것**이 목적이다.
이 전제가 이후 모든 판단의 기준이 된다. 기능을 넣을지 말지 애매할 때는
"이걸 만들면 새로운 난제를 만나는가"로 결정한다. 아니면 만들지 않는다.

## 목표: 세 가지 난이도 축

기능 개수가 아니라 제약의 빡셈으로 키운다.
컨트롤러-서비스-리포지토리를 40번 반복해 쓰는 것은 1번 쓰는 것과 같은 것을 배운다.

| 축 | 이 도메인에서의 기능 | 핵심 난제 | 틀렸을 때 증상 |
|---|---|---|---|
| 쓰기 경합 | 한정 드롭 판매 | 같은 재고에 동시 접근 | 100개 재고가 120개 팔림 |
| 정합성 | 공동구매, 로스터리 정산 | 조건부로 성립하는 거래와 돈 | 공동구매가 깨졌는데 결제는 살아 있음 |
| 읽기 확장 | 레시피 공유와 팔로우 피드 | 소수가 쓰고 다수가 읽음 | 팔로워 많은 계정이 글을 올리면 DB가 죽음 |

커피는 티켓팅과 달리 경합이 도메인에 저절로 내장되어 있지 않다.
**경합이 생기는 자원을 의도적으로 설계에 넣는다** — 한정 드롭, 공동구매 목표 수량,
(이후) 로스터기 배치 용량이 그 장치다.

## 단계

세 축을 동시에 파지 않는다. 한 번에 하나씩 간다.

**단계 구성은 잠정적이다.** 아래 범위와 순서는 지금 시점의 방향일 뿐이며,
학습을 진행하면서 바뀔 수 있다. 앞 단계에서 배운 것이 뒤 단계의 판단을 바꾸는 것이
오히려 정상이다. 미리 전부 확정하면 그것은 추측이 된다.
바뀌면 바뀐 이유와 함께 이 문서를 고친다.

### 1단계 — 한정 드롭 판매 (쓰기 경합)

범위: 로스터리, 원두 상품, SKU(중량·분쇄도), 로스터리 권장 레시피, 재고,
한정 드롭(오픈 시각), 주문, 재고 선점, 결제(가짜 어댑터), OAuth 로그인.

제외: 배송·물류, 리뷰, 검색, 쿠폰, 장바구니, 관리자 기능(데이터는 시드), 실제 PG.

권장 레시피(분쇄도·물 온도·비율·추출 시간)는 `catalog`에 딸린 데이터일 뿐이라
경합이 없고 설계 부담도 없다. 비용이 0에 가까워 1단계에 포함한다.
사용자가 올리는 레시피는 성격이 달라 3단계에서 다룬다.

경합 자원이 **수량형**이라 좌석처럼 흩어지지 않고 재고 레코드 하나에 몰린다.

**락을 미리 걸고 시작하지 않는다.** 락 없이 시작해 초과 판매를 실제로 내고,
STEP을 하나씩 오르며 각 방법이 어디서 무너지는지 측정한다.
락을 처음부터 걸어두면 그 락이 정말 필요한지 영영 알 수 없다.

| | 방법 | 통하는 상황 | 무너지는 지점 |
|---|---|---|---|
| 0 | 락 없음 | — | 초과 판매 발생. 여기서 시작한다 |
| 1 | `synchronized` | 단일 인스턴스 | 인스턴스 2개에서 즉시 깨짐 |
| 2 | 낙관적 락 (`@Version`) | SKU 경합이 흩어진 상태 | 단일 SKU 핫스팟에서 재시도 폭발 |
| 3 | 비관적 락 (`FOR UPDATE`) | 핫스팟에서도 정확 | 커넥션 점유 → 처리량 한계 |
| 4 | Redis 분산락 | DB 부하를 덜어냄 | 락 타임아웃·TTL 만료라는 새 문제 |
| 5 | 대기열 | 경합 자체를 직렬화 | 복잡도, 사용자 대기 UX |

DB 락은 인스턴스가 늘어도 깨지지 않는다. 깨지는 것은 애플리케이션 레벨 락뿐이다.
분산락은 "더 좋은 방법"이 아니라 **다른 트레이드오프**다 — 이전 STEP에 없던 문제가 생긴다.

STEP마다 측정값을 기록한다. 초과 판매 건수, 미판매 잔여 재고, 성공률과 실패 원인 분포,
처리량과 p99, DB 커넥션 대기 시간. 느낌이 아니라 숫자로 판정한다.

**락 전략은 인터페이스로 추상화하지 않는다.** 한 번에 하나만 쓰고 이전 구현은 버린다.
재고 차감 로직을 한 곳에 모아 교체 범위만 좁게 유지한다.

주문은 여러 SKU를 담을 수 있다. 재고 레코드를 여러 개 잠그므로
**락 획득 순서를 전역으로 고정하지 않으면 데드락이 난다**(SKU ID 오름차순).
데드락도 먼저 재현하는 테스트를 만든 뒤 고친다.

결제 재시도로 주문이 중복 생성되지 않도록 **요청 키 기반 멱등성**을 1단계부터 넣는다.
돈이 오가는 연산은 전부 멱등해야 하고, 여기서 습관을 들이지 않으면 2단계에서 다시 만든다.

재고 선점 흐름:

```
재고 가용
  ──주문 생성(선점)──> 주문에 묶임
                        ├─ 결제 성공 ──> 차감 확정
                        ├─ 결제 실패 ──> 복구
                        └─ 시간 만료 ──> 복구
```

만료된 선점은 **lazy 정리를 주 방식으로** 한다. 누군가 그 SKU를 사려는 시점에 함께
정리하므로 경합이 있는 곳에서 자동으로 정리되고 별도 비용이 거의 없다.
아무도 사지 않는 SKU를 위해 주기 배치를 백업으로 둔다. 이 배치는 인스턴스 2개에서
중복 실행되므로 여기서도 분산락이 필요하다 — 4번 STEP의 결과물을 재사용한다.

완료 기준: 한정 드롭 재고 100개에 동시 요청 1,000건이 몰릴 때 성공이 정확히 100건,
최종 재고 0, 초과 판매 0건. 앱 인스턴스를 2개로 늘려도 같은 결과가 나온다.
서로 다른 SKU 조합의 주문이 교차해도 데드락으로 실패하는 요청이 없다.

### 2단계 — 공동구매와 정산 (정합성)

범위: 공동 생두 구매, 결제 승인·확정 분리, 마감 판정, 로스터리 정산, 수수료, 환불.

생두는 마대 단위로 거래되어 개인이 통째로 사기 어렵다. 여러 명이 모여 목표 수량을
채우면 성사되고, 마감까지 미달이면 전원 취소된다. 단순 재고 차감과 구조가 다르다.

| | 일반 판매 (1단계) | 공동구매 (2단계) |
|---|---|---|
| 성립 조건 | 재고만 있으면 즉시 | 목표 수량 도달 + 마감 시각 |
| 실패 가능성 | 없음 | 미달 시 전원 취소 |
| 결제 시점 | 주문 즉시 확정 | 승인만 해두고 성사 후 확정 |

성사 여부를 모르는 채로 돈을 받을 수 없으므로 **결제 승인과 확정을 분리**한다.
1단계가 만들어낸 거래를 정산이 받아먹으므로, 1단계에서 트랜잭션 경계를 대충 그었다면
여기서 드러난다. **1단계 설계를 채점하는 단계다.**

완료 기준: 공동구매 마감 처리 중 임의 지점에 장애를 주입해도 성사 건은 전원 결제 확정,
미성사 건은 전원 승인 취소가 되고 중간 상태로 남는 건이 없다.
원장의 차변 합계와 대변 합계가 일치하고, 불일치 건은 대사 배치가 검출한다.

### 3단계 — 레시피와 피드 (읽기 확장)

범위: 사용자 레시피 공유, 레시피 좋아요, 로스터리·사용자 팔로우, 타임라인,
커서 페이지네이션, 캐시, FCM 푸시 발송.

앞의 두 단계와 결합도가 가장 낮아 마지막에 둔다. 미뤄도 손해가 없고,
의미 있는 측정을 하려면 로스터리·상품 데이터가 이미 쌓여 있어야 한다.

**사용자 레시피가 팬아웃 부하를 만든다.** 타임라인 콘텐츠가 로스터리 드롭 알림뿐이면
발생 빈도가 너무 낮아 푸시형·풀형 선택이 애초에 문제가 되지 않는다. 레시피는 매일
올라오므로 팔로우 그래프를 타고 흐르는 양이 실제로 많아지고, 그제서야 전략 선택이
진짜 문제가 된다.

```
타임라인 = 팔로우한 로스터리의 드롭 (가끔)
         + 팔로우한 사용자의 레시피 (자주)   ← 부하는 여기서 나온다
```

**좋아요 카운터는 1단계 재고 카운터와 좋은 대비가 된다.** 인기 레시피 하나에 쓰기가
몰리는 모양은 같은데 요구사항이 정반대라 해법이 달라진다.

| | 재고 카운터 (1단계) | 좋아요 카운터 (3단계) |
|---|---|---|
| 정확성 | 절대적 — 하나라도 틀리면 초과 판매 | 근사치로 충분 |
| 해법 | 락, 대기열, 직렬화 | 버퍼링, 비동기 집계, 최종 일관성 |
| 우선순위 | 느려도 정확해야 함 | 빨라야 하고 틀려도 됨 |

완료 기준: 대량 데이터를 적재한 상태에서 타임라인 조회 응답 시간이 목표치 이하.
구체적인 건수와 목표 수치는 1·2단계에서 실제 측정값을 확보한 뒤 정한다.

### 이후 후보

세 단계가 끝난 뒤에 검토한다. 지금 설계하지 않는다.

- **로스팅 서비스** — 로스터기 배치 용량이 유한하므로 슬롯 경합이라는 새로운 연습거리가 있다
- **커피 판매** — 드립백·음료

| 모듈 구조 | 1단계는 단일 모듈 | 도메인형 패키지로 경계선만 미리 그어둠. 2단계 정산 진입 시 분리 |
| 데이터베이스 | MySQL | InnoDB 갭락·넥스트키락이 이 프로젝트가 배우려는 함정 그 자체 |
| 캐시·락 저장소 | Redis | 리프레시 토큰, 분산락, 배치 중복 방지. 이후 대기열·캐시 |

## 실행 환경 제약

OCI Always Free 테넌시에서 애플리케이션과 인프라를 함께 돌린다.
아키텍처는 ARM(aarch64)이다.

현행 Always Free 신규 제공량은 상시 약 2 OCPU / 12 GB(월 1,500 OCPU시간 · 9,000 GB시간)이나,
이 테넌시는 이전 제공량인 4 OCPU / 24 GB를 유지하고 있다. 아래 수치는 그 기준이다.

| 항목 | Always Free 한도 |
|---|---|
| 컴퓨트 | **4 OCPU / 24 GB** (`VM.Standard.A1.Flex`) — 콘솔 확인값 |
| 블록 스토리지 | 200 GB (부트 볼륨 + 블록 볼륨 합산) |
| 오브젝트 스토리지 | 20 GB, API 요청 50,000건 / 월 |
| 아웃바운드 전송 | 10 TB / 월 |
| 로드밸런서 | 10 Mbps 고정 |

설계에 미치는 영향:

- **부하 생성기를 서버에 올리지 않는다.** 같은 노드에서 돌리면 부하 도구와 서버가
  CPU를 서로 빼앗아 측정값이 오염된다. 로컬에서 원격 서버를 때린다.
- **로드밸런서 10 Mbps가 부하 테스트의 병목이 될 수 있다.** 측정할 때는 LB를 거치지 않고
  인스턴스를 직접 호출한다. LB는 실제 서비스 경로를 재현할 때만 쓴다.
- **"서버 2대"는 컨테이너 2개로 대체한다.** 프로세스가 분리되면 JVM 내 락은 그대로 깨지므로
  분산락을 배우는 데는 충분하다. 물리 노드를 나눌 필요가 없다.
- **유휴 인스턴스 회수 정책에 걸릴 수 있다.** 7일 동안 CPU 95퍼센타일·네트워크·메모리
  사용률이 모두 20% 미만이면 Oracle이 인스턴스를 회수한다. 인프라 스택을 상시 띄워두면
  메모리 조건은 자연히 벗어난다.
- 개발 장비(Apple Silicon)와 서버가 모두 aarch64라 컨테이너 이미지 아키텍처가 일치한다.
- **부하를 걸 때 CPU 경합에 주의한다.** 4 OCPU에 앱 2개와 MySQL·Redis가 함께 올라가므로,
  부하 수준이 높아지면 STEP 간 성능 차이가 CPU 포화에 가려질 수 있다. 측정할 때 CPU
  사용률을 함께 기록하고, 포화 구간의 수치는 STEP 비교 근거로 쓰지 않는다.
  같은 aarch64 이미지가 로컬(Apple Silicon)에서도 그대로 돌므로 교차 확인이 가능하다.

## 설계 원칙

- **계획은 잠정이다.** 단계의 범위·순서·개수가 모두 학습 중에 바뀔 수 있다.
  계획이 바뀌는 것은 실패가 아니다. 오히려 하나도 안 바뀌었다면 배운 것이 없다는
  신호일 수 있다.
- **현재 단계만 설계한다.** 다음 단계는 자리만 비워둔다. 1단계를 만들기 전에 정산 스키마를
  그리면 그것은 추측이고, 1단계를 끝내면 대개 틀렸다는 것을 알게 된다.
- **모듈은 필요해진 뒤에 가른다.** 미리 나누지 않는다.
- **실제 MySQL·Redis를 쓴다.** 인메모리 DB에 단위 테스트만 돌리면 위 난제들이 아예
  발현되지 않아 연습이 되지 않는다.
- **완료 기준은 측정 가능한 문장으로 쓴다.** "잘 동작한다"가 아니라 숫자로 판정한다.

## 아직 정하지 않은 것

정해질 때마다 이 목록에서 위 본문으로 옮긴다. 이것이 이 문서가 갱신되는 방식이다.

- 배포 방식
- 부하 테스트 도구

## 갱신 규칙

- 단계가 끝나면 완료 기준 달성 여부를 그 단계 항목에 기록한다.
- 미결 항목이 결정되면 본문으로 옮기고 목록에서 지운다.
- 단계 도중 범위가 바뀌면 바뀐 이유를 함께 적는다.

# 00 — 락 없음

- 날짜: 2026-09-24
- 계단: 0 (락 없음)
- 환경: 로컬 / MySQL 8.0 (Testcontainers) / JDK 25

## 무엇을 했나

락을 걸지 않은 재고 차감(`OrderService.placeOrder`)에 동시 요청 1,000건을 넣고
초과 판매가 나는지 관찰했다. 구현은 "조회 → 검사 → 차감 → 저장"이고,
그 사이를 지키는 장치가 없다.

동시 출발은 `CountDownLatch` 두 개로 만들었다. 1,000개 스레드를 하나의 래치에
묶어뒀다가 한 번에 풀고, 다른 래치로 전부 끝날 때까지 기다린다.
`for` 루프로 순차 호출하면 경합이 일어나지 않는다.

측정 도중 커넥션 풀 크기와 `@Transactional` 유무를 바꿔가며 비교했다.
둘 다 동시성 제어 장치가 아닌데도 결과를 바꾸기 때문에,
무엇이 진짜 원인인지 가리려면 따로 떼어 봐야 했다.

## 조건

## 무엇이 무너졌나

**검사와 행동 사이가 벌어졌다.** `if (sku.stock < quantity)`로 검사한 시점의 사실이
UPDATE 시점에도 참이라는 보장이 없다. 10회 × 1,000건 = 10,000번의 검사가 전부
통과했다. 1,000개 스레드가 모두 `stock = 100`을 읽었기 때문이다.
검사 코드는 있었지만 아무것도 막지 못했다.

**쓰기가 절대값이다.** `SET stock = stock - 1`이 아니라 `SET stock = 99`를 쓴다.
읽은 값이 낡았어도 그대로 덮어쓴다. 1,000번 UPDATE했는데 재고는 22 남짓만 줄었다.
978건의 차감이 증발했다 (lost update).

성공 건수가 10회 모두 정확히 1,000이라는 점이 중요하다. 초과 판매 900건은 우연이
아니라 이 코드의 확정적인 동작이다. 흔들리는 것은 최종 재고뿐이고, 그건 차감이
몇 번 살아남았는지가 매번 다르기 때문이다.

### `@Transactional`은 빈도를 낮출 뿐 막지 못한다

트랜잭션을 붙이자 차감 반영이 약 10회에서 22회로 늘고, 재고 편차가 8에서 2로
줄었다. 그런데 **초과 판매는 양쪽 다 정확히 900건**이다.

차감이 더 많이 살아남은 이유는 읽기와 쓰기 사이가 짧아졌기 때문이다. 트랜잭션이
없으면 SELECT 후 커넥션을 반납하고 다시 줄을 서야 해서, 낡은 값을 든 채 기다리는
시간이 길다. 트랜잭션이 있으면 읽기부터 커밋까지 한 구간에 붙어 있고 UPDATE의 행
잠금이 커밋까지 유지되어 쓰기가 직렬화된다.

편차가 줄어든 것은 실행 패턴이 일정해졌기 때문이고, 14% 느려진 것은 커넥션을
커밋까지 쥐고 있어 풀 회전율이 떨어졌기 때문이다.

정확한 시스템이라면 재고 0, 성공 100, 실패 900이어야 한다. 양쪽 다 근처에도 가지
못했다. **편차가 줄어든 것이 오히려 위험하다** — 매번 비슷한 숫자가 나오면 정상
동작으로 착각하기 쉽다.

트랜잭션이 필요한 이유는 따로 있다. 트랜잭션이 없으면 리포지토리 호출마다 경계가
갈려서, 재고 차감은 커밋됐는데 주문 저장이 실패하면 재고만 증발한다.
`@Transactional`은 그 원자성을 위해 필요하고, 동시성은 별개 문제다.

### 커넥션 풀은 직렬화 장치가 아니다

트랜잭션 없이 풀만 50 → 5로 줄였을 때 초과 판매는 그대로 900건이었다.
예상(재고가 바닥나 실패가 발생)이 빗나갔다.

원인은 **커넥션 점유 시간과 위험 구간의 길이가 다르다**는 데 있다. 트랜잭션이 없으면
SELECT가 커넥션을 짧게 쓰고 반납한 뒤, 스레드는 낡은 값을 자바 힙에 든 채로
UPDATE 차례를 기다린다. 풀이 제한하는 것은 앞엣것뿐이다.
오히려 대기가 길어져 읽기-쓰기 간격이 벌어졌고, 소요 시간만 1,668 → 2,104ms로 늘었다.

`@Transactional`을 붙이면 커넥션을 커밋까지 쥐고 있으므로 이 둘이 같아진다.
풀 5 + 트랜잭션에서 초과 판매가 900 → 375로 줄어든 것이 그 결과다.
다만 이것은 락이 막아준 것이 아니라 풀 크기가 우연히 동시 실행 수를 제한한 것이고,
풀을 50으로 올리면 그대로 무너졌다.

## 다음에 할 것

계단 1 — `synchronized`로 재고 차감을 막는다. 확인할 것은 둘이다.

- 초과 판매가 0이 되는가
- 소요 시간이 얼마나 나빠지는가 (기준선 2,249ms)

주의할 점이 하나 있다. `@Transactional`은 AOP 프록시가 메서드 **바깥**에서 여닫고
`synchronized`는 메서드 **안**에 있다. 락이 먼저 풀리고 커밋이 나중이므로, 그 틈에
들어온 스레드는 아직 커밋되지 않은 재고를 읽는다. 락을 트랜잭션보다 바깥에 두어야 한다.

그 다음 인스턴스 2개로 같은 테스트를 돌려 `synchronized`가 JVM 하나 안에서만
유효하다는 것을 확인한다.

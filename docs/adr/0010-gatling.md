# ADR-0010: 부하 도구로 Gatling 채택

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: [ADR-0009](0009-testcontainers.md)

## 배경

계단 1부터는 앱 인스턴스를 2개로 띄워 검증해야 하는데,
JVM 내부 통합 테스트로는 재현할 수 없다([ADR-0009](0009-testcontainers.md)).
서버 외부에서 부하를 거는 도구가 필요하다.

## 결정

**Gatling**(Kotlin DSL)을 쓴다. 시나리오는 Gatling Gradle 플러그인의 소스셋에 둔다.

부하 생성기는 **항상 서버 외부에서** 실행한다.

## 근거

- 시나리오를 Kotlin으로 써서 프로젝트와 언어가 통일된다.
- HTML 리포트가 상세해서 계단별 측정 기록에 그대로 쓸 만하다.
- 측정 머신(로컬 Apple Silicon)이 JVM 부담을 감당할 수 있다.

## 기각한 대안

**k6** — Go 단일 바이너리라 더 가볍고 측정 머신 자원을 덜 먹는다.

기각 이유: 시나리오가 JavaScript라 언어가 갈린다. 가볍다는 이점은 로컬 측정 머신이
충분히 강력해서 결정적이지 않았다.

**JMeter** — GUI 기반이라 시나리오를 코드로 관리하기 어렵고 버전 관리에 불리하다.

## 결과

- **부하 생성기를 서버와 같은 노드에서 돌리지 않는다.** 같은 노드에서 돌리면
  부하 도구와 서버가 CPU를 서로 빼앗아 측정값이 오염된다.
- OCI 로드밸런서(10 Mbps)를 거치지 않는다. 측정 시에는 nginx 컨테이너 또는
  인스턴스를 직접 호출한다.
- 측정할 때 CPU 사용률을 함께 기록하고, 포화 구간의 수치는 계단 비교 근거로 쓰지 않는다.
- Gatling Gradle 플러그인의 Kotlin 소스셋 경로는 도입 시점에 문서로 확인한다
  (`src/gatling/kotlin`으로 예상).

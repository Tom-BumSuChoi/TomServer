# ADR-0006: OAuth 서버 주도 흐름과 자체 토큰 발급

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: [ADR-0007](0007-fcm-push.md)

## 배경

클라이언트는 모바일 앱(Android + iOS)이고, 인증은 OAuth만 쓰기로 했다.
그런데 **앱은 아직 존재하지 않는다.** 1단계 서버가 돌아간 뒤에 착수한다.

## 결정

**서버 주도 Authorization Code 흐름**을 쓴다. 프로바이더는 구글부터 시작한다.

```
앱 ──시스템 브라우저──> 서버 /oauth2/authorization/google
서버 <──인가 코드 교환──> 구글
앱 <──커스텀 스킴(tomserver://)── 서버가 발급한 자체 토큰
```

서버는 소셜 토큰을 그대로 쓰지 않고 **자체 토큰을 발급**한다.

| | 액세스 토큰 | 리프레시 토큰 |
|---|---|---|
| 형태 | 자체 JWT | 불투명 문자열 |
| 만료 | 짧게 (30분 내외) | 길게 (2주 내외) |
| 저장 | 안 함 (stateless) | Redis |

리프레시 토큰은 회전하고, 한 번 쓴 토큰이 다시 들어오면 탈취로 간주해
해당 사용자의 전체 세션을 무효화한다.

## 근거

- **앱이 없어도 브라우저만으로 전 과정을 테스트할 수 있다.** 이것이 결정적이었다.
  앱 주도를 택하면 1단계 내내 인증을 우회하거나 가짜 토큰을 쓰게 된다.
- Spring Security OAuth2 Client를 표준대로 쓰게 된다. 학습량이 더 많다.
- 프로바이더 추가가 설정 몇 줄이다.
- 액세스 토큰이 stateless라 앱 인스턴스가 몇 대든 상관없다. 상태를 갖는 것은
  리프레시 토큰뿐이고, 그것을 Redis에 두면 인스턴스 간 공유가 해결된다.

## 기각한 대안

**앱 주도 SDK 흐름** — 앱이 카카오·구글 SDK로 로그인해 받은 토큰을 서버가 검증만 하는 방식.
국내 앱 대부분이 쓰고 UX가 더 낫다.

기각 이유: 앱이 없어 개발 중 토큰을 얻을 방법이 없다. 서버 입장에서는 "토큰 받아
검증하는 엔드포인트" 하나라 배울 것도 적다. 다만 **두 방식은 공존 가능하므로**,
앱이 생긴 뒤 UX가 필요하면 엔드포인트를 추가하면 된다. 되돌릴 수 없는 결정이 아니다.

**Firebase Authentication** — 회원가입·비밀번호·소셜 로그인·이메일 인증을 통째로
아웃소싱할 수 있다.

기각 이유: OAuth만 쓰기로 한 이상 Firebase Auth가 끼어들 자리가 없고,
외부 의존이 하나 늘어난다. 인프라를 OCI에 모으는 구성과도 어긋난다.

## 결과

- 리프레시 토큰 회전과 재사용 탐지를 직접 구현한다. "토큰 갱신 도중 앱이 죽으면?"
  같은 경계 상황을 만나게 된다.
- **Redis가 유실되면 전원 로그아웃된다.** 연습 프로젝트에서는 감수할 만한 대가다.
- 인증이 난이도 세 축과 무관해 보이지만, 리프레시 토큰 부분만은 다중 인스턴스 문제와
  정면으로 얽힌다.
- iOS 앱 심사에서 Apple 로그인이 요구될 수 있다. 프로바이더 추가로 대응 가능하므로
  앱 착수 시점에 확인한다.
- **푸시에는 Firebase를 쓴다**([ADR-0007](0007-fcm-push.md)). 인증에만 쓰지 않는 것이다.

# ADR-0005: MySQL 채택

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: [ADR-0001](0001-three-difficulty-axes.md), [ADR-0009](0009-testcontainers.md)

## 배경

1단계의 핵심은 락 전략을 계단식으로 교체하며 각각이 어디서 무너지는지 측정하는 것이다.
락 동작과 격리 수준은 DB 구현마다 다르므로, 무엇을 쓰느냐가 학습 내용을 직접 좌우한다.

## 결정

MySQL(InnoDB)을 쓴다.

## 근거

- 이 프로젝트의 목적은 락 동작을 몸으로 배우는 것이고, **MySQL이 더 많이 물어뜯는다.**
- InnoDB의 갭락·넥스트키락은 실무 데드락의 주요 원인이다. 기본 격리 수준이
  `REPEATABLE READ`라 예상과 다르게 동작하는 지점이 많다.
  **함정이 많은 것이 연습 프로젝트에서는 장점이다.**
- 국내 실무 비중이 높아 자료가 많고, 여기서 겪은 문제가 그대로 재사용된다.

## 기각한 대안

**PostgreSQL** — 락 동작이 더 직관적이고 예측 가능하며, 3단계 읽기 최적화에서 쓸
도구(윈도우 함수, CTE, 부분 인덱스, JSONB)가 훨씬 풍부하다.

기각 이유: 예측대로 동작하는 DB에서는 배울 것이 적다. 3단계 이점은 인정하지만
1단계의 학습 밀도를 우선했다.

대기열에 필요한 `SKIP LOCKED`는 양쪽 모두 지원하므로 판단 기준이 되지 않았다.

## 결과

- 갭락·넥스트키락·격리 수준에서 비롯된 실패를 실제로 겪게 된다. 이것이 의도한 바다.
- Testcontainers로 실제 MySQL을 띄워 테스트한다 ([ADR-0009](0009-testcontainers.md)).
- JPA 방언과 마이그레이션이 MySQL 기준으로 고정된다.
- 3단계 읽기 최적화에서 도구가 부족하다고 판단되면 그 시점에 재검토하고,
  결론이 바뀌면 이 ADR을 대체하는 새 ADR을 쓴다.
